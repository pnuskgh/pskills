# Create Agent — 에이전트 채용 담당자

에이전트 1명을 "직원 채용"에 비유해 정의한다: 직무 파악 → 위치 결정 → 중복 검토 → 채용 조건(도구·모델) 결정 → 채용 공고(정의 파일) 작성 → 업무 자료 준비 → 검증. 여러 에이전트가 팀으로 실시간 협업해야 하는 대규모 구축 요청이면 `harness` 스킬로 넘긴다.

## 워크플로우

### 1. 요구사항 파악 (직무 정의)

다음이 불명확하면 사용자에게 먼저 묻는다 — 추측해서 채우지 않는다.
- **담당 업무**: 정확히 무엇을 하는 에이전트인가?
- **호출 방식**: 사람이 `subagent_type`으로 직접 지명해서 부를 것인가, Claude가 요청 내용을 보고 자동으로 골라야 하는가? (자동 선택이 필요하면 description을 더 구체적으로 써야 한다 — 4단계 참조)
- **산출물**: 무엇을 반환하는가? (보고서, 코드 변경, 파일 등)

### 2. 위치 결정

| 위치 | 적합한 경우 |
|------|-----------|
| `~/.claude/agents/{name}.md`(전역) | 여러 프로젝트에서 재사용할 범용 직무 (예: 코드 리뷰어, 리서치 담당) |
| `프로젝트/.claude/agents/{name}.md`(프로젝트 로컬) | 이 저장소의 파일 구조·컨벤션·도메인에 종속된 직무 |

애매하면 사용자에게 묻는다.

### 3. 중복 검토

신규 채용 전, 빌트인 타입(`general-purpose`, `Explore`, `Plan` 등 — 세션에 안내된 목록 참고)과 기존 `.claude/agents/*.md`를 훑어 역할이 겹치는지 확인한다.

| 상황 | 조치 |
|------|------|
| 빌트인 타입만으로 충분한 역할 | 빌트인 타입을 `subagent_type`으로 쓰되, 정의 파일은 그래도 만든다 |
| 기존 정의 파일이 신규 역할을 대부분 포함 | 신규 채용 금지 — 기존 에이전트 확장을 제안 |
| 역할이 명확히 다름 | 신규 채용 진행 |

**빌트인 타입이라도 예외 없이 정의 파일을 만든다.** create-agent를 쓴다는 것 자체가 "재사용할 역할을 채용하겠다"는 뜻이다. 정의 파일 없이 프롬프트에 역할을 직접 넣으면 다음 세션에서 재사용할 수 없고, 호출할 때마다 역할·원칙이 미묘하게 달라져 품질이 흔들린다.

### 4. Description 작성 — 채용 공고 헤드라인

Description은 두 가지 역할을 한다: **(a)** 사람이 언제 이 에이전트를 지명할지 판단하는 문서, **(b)** Claude가 요청 내용만 보고 자동으로 이 에이전트를 고를지 판단하는 유일한 근거. 스킬 description과 마찬가지로 트리거를 보수적으로 판단하는 경향을 보상하기 위해 약간 "pushy"하게 쓴다.

**나쁜 예:** `"코드를 리뷰하는 에이전트"` — 모호, 언제 호출해야 하는지 불분명.
**좋은 예:** `"PR이나 diff의 정확성·재사용성·효율성을 검토. '리뷰해줘', '이 변경 괜찮아?' 요청에 사용. 단, 코드 스타일/포맷팅만 확인하면 되는 요청에는 사용하지 말 것(그런 요청은 기본 도구로 충분)."`

**후속 호출·이어가기가 필요한 역할**이면(예: 장시간 조사, 상태를 유지하는 역할) description에 "최근에 이미 spawn된 동일 역할 에이전트가 있으면 새로 만들지 말고 이어서 사용할 것" 같은 지침을 넣어 중복 채용을 막는다.

**명시적 호출 규칙 표기:** 사용자가 채팅에 `!!{name}`이라고 입력하면, 이 에이전트를 `subagent_type: "{name}"`으로 즉시 호출하라는 명시적 지시다. 새로 만드는 모든 에이전트의 description 끝에 이 규칙을 한 줄 덧붙인다 — 예: `"...(역할 설명). 사용자가 '!!{name}'이라고 입력하면 이 에이전트를 직접 호출한다."` description에 박아 둬야, 이 스킬 없이 에이전트 목록만 보는 다른 세션에서도 호출 규칙을 바로 알 수 있다.

### 5. 근무 조건 결정 — tools / model

- **tools (도구 권한)**: 이 직무에 실제로 필요한 도구만 부여한다 — 최소 권한 원칙. 예: 조사만 하면 `Read, Grep, Glob`, 코드도 고쳐야 하면 `+Write, Edit, Bash`. 생략하면 모든 도구를 상속하므로, 그래야 할 명확한 이유가 있을 때만 생략한다.
- **model (직급)**: 업무 난이도에 맞춰 고른다.

| 모델 | 적합한 역할 |
|------|-----------|
| `opus` | 복잡한 설계·추론·품질이 핵심인 역할 (아키텍처 결정, 심층 리뷰) |
| `sonnet` | 범용 엔지니어링 작업의 기본값 |
| `haiku` | 단순·반복·고빈도라 속도/비용이 중요한 역할 |
| `inherit` | 부모 대화와 같은 모델 사용 — 특별한 이유가 없다면 명시하지 않는 편이 유연하다 |

### 6. 시스템 프롬프트(본문) 작성 원칙

| 원칙 | 설명 |
|------|------|
| **Why를 설명하라** | 강압적 규칙 대신 이유를 전달한다 — 이유를 이해해야 엣지 케이스에서도 올바르게 판단한다. |
| **명령형으로 작성** | "~한다", "~하라" 형태. 정의 파일은 그 에이전트의 시스템 프롬프트다. |
| **일반화하라** | 특정 예시에만 맞는 좁은 규칙 대신 원리를 설명한다. |
| **Lean하게 유지** | 반복 참고할 긴 자료는 본문에 넣지 말고 7단계의 업무 자료 폴더로 분리한다. |

**필수 섹션**: 핵심 역할 / 작업 원칙 / 입력·출력 프로토콜 / 에러 핸들링 / 협업(사용자·다른 에이전트와의 관계). 입력·출력 프로토콜에는 7단계에서 정한 `MEMORY-{name}.md`·`docs/agent-{name}/` 사용 규칙을 포함한다. 여러 에이전트가 팀으로 협업하는 역할이면 `## 팀 통신 프로토콜`(SendMessage 대상, 작업 요청 범위)을 추가한다.

**스킬 활용 명시**: 이 에이전트가 기존 스킬을 써야 하는 역할이면, 아래 세 가지 중 어떤 방식으로 쓸지 본문에 명시한다 — 명시하지 않으면 에이전트가 스킬 존재 자체를 놓치기 쉽다.

| 방식 | 구현 | 적합한 경우 |
|------|------|-----------|
| Skill 도구 호출 | 본문에 "Skill 도구로 `/skill-name` 호출"이라고 명시 | 스킬이 독립 워크플로우이고 사용자도 직접 호출 가능한 경우 |
| 프롬프트 내 인라인 | 스킬 내용을 본문에 직접 포함 | 스킬이 짧고(50줄 이하) 이 에이전트 전용인 경우 |
| 레퍼런스 로드 | `Read`로 스킬의 `references/` 파일을 필요할 때만 로드 | 스킬 내용이 크고 조건부로만 필요한 경우 |

재사용성이 높으면 Skill 도구 호출, 이 에이전트 전용이면 인라인, 대용량이면 레퍼런스 로드를 택한다.

### 7. 에이전트가 쓰는 폴더/파일 — 3종류를 구분한다

에이전트 하나가 다루는 데이터는 성격이 다른 세 곳에 나뉘어 저장된다. 셋을 섞으면(예: 정적 참고자료 폴더에 매번 작업 산출물을 쌓는 식) 나중에 어디에 뭐가 있는지 찾기 어려워지므로 반드시 구분한다.

```
.claude/agents/
├── {name}.md                  (필수 — frontmatter + 시스템 프롬프트)
└── {name}/                    (선택 — 에이전트가 참고하는 정적 자료)
    ├── references/             (역할 수행에 필요한 도메인 지식, 체크리스트)
    ├── templates/               (산출물 템플릿)
    └── scripts/                 (반복 작업용 실행 코드)

{현재 폴더}/                    (이 에이전트를 채용하는 프로젝트의 루트 — 저장소 루트일 수도, 그 안의
│                                하위 프로젝트 폴더일 수도 있다. 애매하면 사용자에게 확인한다)
├── MEMORY-{name}.md            (에이전트의 장기 기억)
└── docs/
    └── agent-{name}/            (에이전트가 사용자 요청을 처리하며 생성·참조하는 작업 산출물)
```

- **`.claude/agents/{name}/` — 참고 자료**: 스킬의 `references/`·`scripts/`·`assets/`와 같은 목적으로, 에이전트가 "어떻게 일할지"를 정의하는 정적 자료다. 에이전트에는 `${SKILL_DIR}` 같은 자동 변수가 없으므로 **정의 파일 본문에서 이 폴더의 경로를 직접 문장으로 명시**해야 실제로 찾아 읽는다. 참고할 자료가 없는 단순한 역할이면 폴더를 억지로 만들지 않는다 — 빈 폴더는 산출물이 아니다.
- **`{현재 폴더}/MEMORY-{name}.md` — 장기 기억**: 세션이 끝나도 남아야 하는 맥락(과거 판단, 사용자 피드백, 반복되는 학습)을 적는 파일. 모든 에이전트 정의 본문에 "작업 시작 시 이 파일을 읽고, 끝나면 중요한 내용을 추가한다"는 규칙을 넣는다. 파일은 처음 기록할 내용이 생겼을 때 만들면 되고, 빈 파일을 미리 만들어 둘 필요는 없다.
- **`{현재 폴더}/docs/agent-{name}/` — 작업 산출물**: 사용자가 요청한 작업을 처리하는 동안 만들거나 참조한 데이터(보고서, 조사 결과, 생성물)를 쌓는 곳. `.claude/agents/{name}/`과 달리 매번 늘어나는 결과물이 여기 들어간다. **하위 구조는 고정 템플릿을 쓰지 말고, 그 에이전트가 실제로 다루는 산출물 종류에 맞춰 그때그때 제안한다** — 예: 조사 대상별로 나뉘면 `research/{대상}.md`, 비교 산출물이 따로 있으면 `comparisons/`처럼 그 에이전트의 업무 성격을 반영한다.

### 8. 작성 및 검증

1. `{위치}/.claude/agents/{name}.md`를 frontmatter(`name`, `description` 필수, 필요 시 `tools`/`model`) + 시스템 프롬프트로 작성한다.
2. 필요한 참고 자료가 있으면 `{위치}/.claude/agents/{name}/`을 만들고, 본문에서 경로를 참조하게 한다.
3. 본문에 `{현재 폴더}/MEMORY-{name}.md`(장기 기억)와 `{현재 폴더}/docs/agent-{name}/`(작업 산출물, 제안한 하위 구조 포함) 사용 규칙을 명시한다.
4. **호출 검증**: `subagent_type: "{name}"`으로 직접 호출하는 시나리오와(해당되면) description만으로 Claude가 자동으로 이 에이전트를 고르는 시나리오를 한두 개 점검한다.
5. 사용자에게 생성 경로, 부여한 도구, 모델 선택 이유를 요약 보고한다. 실제 실행 테스트는 별도 요청 시에만 수행한다.

## 산출물 체크리스트

- [ ] 직무(역할/호출 방식/산출물) 파악 완료
- [ ] 위치(전역/프로젝트 로컬)를 사용자와 확인함
- [ ] 빌트인 타입·기존 에이전트와 중복 검토 완료
- [ ] `tools`를 최소 권한으로 지정 (상속이면 그 이유가 명확함)
- [ ] `model`을 역할 난이도에 맞게 선택
- [ ] `description`이 적극적으로 작성됨 (하는 일 + 호출 상황 + 경계)
- [ ] `description`에 `!!{name}` 명시적 호출 규칙을 한 줄 포함함
- [ ] 본문이 명령형·Why-first로 작성되고 필수 섹션(핵심 역할/작업 원칙/입출력/에러 핸들링/협업)을 포함
- [ ] 스킬을 활용하는 역할이면 활용 방식(Skill 도구/인라인/레퍼런스 로드)을 본문에 명시함
- [ ] 참고 자료가 있을 때만 `.claude/agents/{name}/` 폴더를 만들고 본문에서 경로를 명시함
- [ ] 본문에 `{현재 폴더}/MEMORY-{name}.md`(장기 기억) 사용 규칙을 명시함
- [ ] 본문에 `{현재 폴더}/docs/agent-{name}/`(작업 산출물) 사용 규칙과, 그 에이전트 업무에 맞춘 하위 구조 제안을 명시함

## 참고

팀 통신 프로토콜, 에이전트 분리 기준, 실행 모드 선택(에이전트 팀 vs 서브 에이전트), 아키텍처 패턴 등 더 깊은 설계와 실제 예시가 필요하면 `references/agent-design-patterns.md`와 `references/team-examples.md`를 읽는다.

QA(품질 검증) 역할을 채용할 때는 반드시 `Explore`가 아닌 `general-purpose` 타입을 기반으로 하고(검증 스크립트 실행 필요), "존재 확인"이 아닌 "경계면 교차 비교"에 집중해야 한다 — 상세 가이드와 정의 템플릿은 `references/qa-agent-guide.md`를 읽는다.

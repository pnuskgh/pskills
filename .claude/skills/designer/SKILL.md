# Designer — 화면 디자인

화면은 사람이 보고 쓰는 것이다. "예쁘게 해줘" 같은 모호한 요청을 순서가 정해진 절차로 바꿔서, 결과가
감(taste)이 아니라 원칙에 의해 옳아지도록 만든다.

## 작업 단계 — 구조 → 기능 → 디자인 폴리싱

화면 하나를 구조·기능·비주얼까지 한 번에 완성하려고 하면, 뒤에서 뭔가 바뀔 때(레이아웃이 잘못됐다,
데이터 모양이 다르더라) 앞서 들인 폴리싱 공수를 그대로 버리게 된다. 그래서 되돌리는 비용이 싼
결정부터 순서대로 굳힌다 — 아래는 그 기본 3단계다(작업 성격에 따라 세부는 조정해도 되지만, "구조가
안 잡힌 채로 폴리싱하지 않는다"는 순서 자체는 지킨다).

1. **구조(Structure)** — 정보 위계와 레이아웃 뼈대만 잡는다. 색상/그림자/둥근 모서리 같은 폴리싱
   요소는 아직 손대지 않고, 중립 배경과 실제(또는 대표) 콘텐츠로 "어디에 무엇이 있는가"만 확정한다.
   `design-guide.md` 확인/생성(아래 작업 절차 1번)도 이 단계에서 한다 — 이후 단계가 쓸 기준이 여기서
   정해진다.
2. **기능(Function)** — 실제 컴포넌트(Button/Card/Input 등)로 바꾸고, 데이터 연결·상태 관리·
   인터랙션(클릭, 폼 제출, 로딩/에러/빈 상태)을 실제로 동작하게 만든다. 비주얼 디테일(정확한 색,
   간격 미세조정, 애니메이션)은 아직 미루고 라이브러리 기본 스타일 그대로 둔다.
3. **디자인 폴리싱(Polish)** — 구조와 기능이 안정된 뒤에, 아래 "판단 순서"를 순서대로 적용해 비주얼을
   다듬는다. 반응형 세부 확인·다크모드 확인·접근성 대비 확인·`design-guide.md` 갱신도 이 단계에서
   한다(아래 작업 절차 2~7번).

**단계마다 끝에서 실제로 렌더링해서 확인한 뒤 다음 단계로 넘어간다** — 구조가 잘못된 채로 기능을
붙이거나, 기능이 안 되는 채로 폴리싱하지 않는다. 규모가 큰 작업(새 화면 여러 개, 대시보드 전체 등)이면
구조 단계 결과를 보여주고 방향이 맞는지 확인받는 것도 고려한다 — 사람이 뒤늦게 "레이아웃부터
다시"라고 하면 그게 가장 비싼 되돌리기다.

**예외**: 이미 구조·기능이 있는 화면을 다듬는 요청("이 버튼 색 바꿔줘", "여백 좀 넓혀줘")은 해당
단계(대개 폴리싱)로 바로 들어간다 — 안 바뀌는 단계를 형식적으로 거치지 않는다.

## 판단 순서 — 디자인 폴리싱 단계에서 이 순서를 지켜야 하는 이유

색상은 항상 **마지막**에 손댄다. 대부분의 나쁜 디자인은 색상부터 고치려다가 생긴다 — 레이아웃이
망가진 화면은 팔레트를 아무리 잘 골라도 나아지지 않고, 오히려 근본 문제(정보 위계, 여백, 컴포넌트
불일치)를 가려서 더 늦게 발견되게 만든다. 항상 아래 순서로 판단한다.

1. **정보 위계** — 이 화면에서 사용자가 가장 먼저 봐야 할 것은 무엇인가? 그다음은? 위계가 불명확하면
   레이아웃을 아무리 배치해도 산만해진다.
2. **레이아웃/그리드** — 위계를 공간 배치로 옮긴다. 새 그리드 체계를 발명하지 않는다 — 이미 이
   프로젝트가 쓰는 레이아웃 컨벤션(예: Tailwind의 `max-w-*`/`grid-cols-*`, 기존 페이지들의 여백 패턴)을
   먼저 찾아서 그대로 따른다.
3. **컴포넌트 재사용** — 새 컴포넌트를 만들기 전에 기존 컴포넌트로 될지 먼저 확인한다. 버튼/카드/폼
   필드가 화면마다 미묘하게 다르면, 사용자는 그걸 "다른 것"으로 인식해 혼란을 겪는다.
4. **여백과 리듬** — 프로젝트의 spacing scale(예: 4px 배수)을 임의의 px 값보다 우선한다. 요소 간
   여백이 불규칙하면 다른 걸 다 잘해도 화면이 "정돈 안 된" 느낌을 준다.
5. **타이포그래피** — 폰트 크기/굵기 단계를 이미 쓰는 것에서 고른다(새 크기를 즉흥적으로 추가하지
   않는다). 제목-본문-보조텍스트의 대비가 위계를 다시 한번 강화해야 한다. **주요 사용자의 언어가
   UI 킷 기본 폰트의 지원 문자 체계 밖이면 폰트 자체를 바꾼다** — shadcn 같은 UI 킷 프리셋의 기본
   폰트는 보통 라틴 전용이라, 한국어처럼 라틴이 아닌 문자가 주력인 사이트에 그대로 쓰면 해당 문자는
   조용히 시스템 폰트로 폴백되어 나머지 UI와 톤이 어긋난다(실측: Geist Variable은 한글 글리프가 없다
   — Pretendard처럼 그 문자 체계를 실제로 포함하면서 라틴 쪽 톤도 기존 폰트와 맞는 대안을 찾는다).
   프리셋 기본값을 검증 없이 그대로 받아들이지 않는다.
6. **색상** — 마지막. 이미 프로젝트에 디자인 토큰/팔레트가 있으면 그대로 쓴다. 새로 정해야 한다면
   최소한으로: 브랜드색 1~2개 + 중립 그레이 스케일 + 상태색(성공/경고/위험)만으로 시작한다.
7. **모션(선택)** — 상태 전환이 갑작스러우면 짧은 트랜지션만 추가한다. 화려한 애니메이션을 요청받지
   않았다면 추가하지 않는다.

## 작업 절차

1. **`design-guide.md`부터 찾는다 — 있으면 그게 기준, 없으면 만든다.** 작업 중인 프론트엔드 프로젝트
   루트(`package.json`이 있는 위치)에서 `design-guide.md`를 찾는다. 모노레포에서 프론트엔드 앱이
   여러 개면 지금 작업 중인 그 앱의 루트를 본다(앱마다 다른 UI 라이브러리를 쓸 수 있다).
   - **있으면**: 그 내용이 이 스킬의 판단 순서보다 우선한다 — 이 스킬은 프로젝트에 아직 정해진 게
     없을 때 쓰는 기본값일 뿐이다. 기존 화면 몇 개를 훑는 것보다 이 파일 하나를 읽는 게 더 정확하다
     (화면들이 서로 어긋나 있을 수 있지만 이 파일은 의도된 기준이다).
   - **없으면**: 참고할 기존 화면이 있다면 2~3개를 훑어 관례를 역산하고, 없다면(막 새로 시작하는
     프로젝트, 또는 기존 화면을 참고하지 말라는 지시를 받은 경우) 이미 설치된 UI 라이브러리(예:
     shadcn/ui, MUI, Chakra)가 있으면 그 컴포넌트/토큰을, 없으면 이 스킬의 판단 순서 6번 색상
     기본값(중립 그레이 + 브랜드색 1~2개)과 4px 배수 spacing scale을 최소 토큰으로 삼는다. 이렇게
     파악·결정한 내용을 바로 `design-guide.md`로 적어 만든다(작성 구조는
     `references/design-guide-template.md` 참고) — 화면을 보고 다시 추측하지 않도록, 다음 작업부터는
     이 파일이 곧 "기존 관례"가 되게 한다.
2. **위 판단 순서대로 하나씩 적용한다.** 색상 얘기가 먼저 나오는 요청("파란색으로 바꿔줘" 등)이라도,
   레이아웃/여백에 명백한 문제가 보이면 먼저 짚어주고 사용자에게 알린다 — 조용히 범위를 넘어서
   고치지는 않는다.
3. **반응형을 실제로 확인한다.** 브레이크포인트 클래스만 넣고 끝내지 않는다 — 가능하면 브라우저를
   열어 폭을 줄여가며 실제로 깨지는 지점이 없는지 확인한다(1단계 6-1절 같은 "수동 확인" 항목을
   완료 표시만 하고 건너뛰지 않는다). 브라우저 자동화가 없는 환경이면, 확인하지 못했다는 사실을
   숨기지 말고 명시한다.
4. **접근성을 기본값으로 취급한다** — 별도 요청이 없어도 항상 확인: 텍스트/배경 대비가 최소
   WCAG AA(4.5:1, 큰 텍스트는 3:1)를 넘는가, 인터랙티브 요소에 포커스 상태가 있는가, 색상만으로
   상태를 구분하지 않는가(아이콘/텍스트 병행), 시맨틱 태그(`button`, `nav`, `label` 등)를 쓰는가.
   대비는 색상 이름/진하기를 보고 짐작하지 말고 실제로 계산한다 — 같은 브랜드 색이라도 배경을 꽉
   채우는 용도(버튼 등, 배경 자체가 불투명해서 페이지 테마와 무관하게 대비가 고정됨)와 배경 없이
   텍스트로만 쓰는 용도(링크 등, 그 텍스트가 올라앉는 페이지 배경에 따라 대비가 달라짐)는 같은 값이
   통과/미달 여부가 갈릴 수 있다(실측: blue-600은 흰 버튼 텍스트로 5.17:1 통과, 다크 배경 위 텍스트로는
   3.77:1 미달). 하나의 토큰 값이 모든 용도에 항상 안전하다고 가정하지 않는다.
5. **다크모드가 이미 있는 프로젝트라면** 라이트 모드만 고치고 끝내지 않는다 — 두 모드 다 같은 순서로
   확인한다.
6. **결과를 실제로 렌더링해서 본다.** 코드만 고치고 끝내지 않는다 — dev 서버를 띄우거나 스크린샷을
   찍어 실제로 어떻게 보이는지 확인한 뒤에 완료로 보고한다. 보지 않은 디자인은 완성된 게 아니다.
7. **`design-guide.md`를 최신 상태로 유지한다.** 이번 작업에서 앞으로도 반복될 만한 결정(새 컴포넌트
   스타일을 정했다, 색상/스페이싱 기본값을 바꿨다, 새 브레이크포인트 규칙을 도입했다 등)을 내렸다면,
   끝내기 전에 `design-guide.md`에 그 내용을 반영한다 — 그래야 다음 화면 작업 때 이번에 한 고민을
   또 하지 않는다. 이번 화면 하나에만 해당하는 사소한 값(예: 이 카드 하나만 특별히 넓은 padding)은
   적지 않는다 — 다른 화면에도 재사용될 규칙만 올린다.

## 스택별 실행 — React + Vite

위 원칙을 이 스택에서 구체적으로 어떻게 실행하는지다. 다른 프레임워크(Vue, Svelte 등)를 만나면 같은
원칙을 그 프레임워크의 관용구로 바꿔 적용한다 — 아래는 원칙이 아니라 실행 디테일이다.

- **컴포넌트 재사용(판단 순서 3번)**: 화면(페이지) 컴포넌트 안에 버튼/카드/폼 필드 스타일을 매번 새로
  작성하지 않는다. 반복되는 UI는 `props`로 variant를 받는 프레젠테이션 컴포넌트로 뽑아
  (`<Button variant="primary" />`처럼) 재사용한다 — 화면 두 개째부터 같은 요소를 다시 마크업하고
  있다면 그 시점에 컴포넌트로 추출한다.
- **스타일링 일관성(판단 순서 4~6번)**: Tailwind를 쓰는 프로젝트라면 같은 유틸리티 클래스 조합이
  여러 파일에 반복되는지 살핀다 — 반복되면 컴포넌트로 뽑거나(위 항목), `clsx`/`cva` 같은 걸 이미
  쓰고 있으면 그 패턴을 따른다. CSS 모듈/styled-components를 쓰면 그쪽 관례를 그대로 따른다 — 한
  프로젝트 안에서 스타일링 방식을 섞어서 새로 도입하지 않는다.
- **실제로 렌더링해서 본다(작업 절차 6번)**: Vite dev 서버(`bun run dev`/`npm run dev`)를 띄우고
  브라우저로 확인하는 게 기본이다. 브라우저 자동화 도구가 있으면 그걸로, 없으면 최소한 개발자 도구의
  디바이스 툴바로 폭을 줄여가며(작업 절차 3번, 반응형) 실제로 깨지는 지점을 확인한다 — Vite는 HMR이
  빨라서 이 확인·수정 반복 자체가 느리지 않다는 걸 활용한다.
- **접근성(작업 절차 4번)을 JSX에서 놓치기 쉬운 지점**: 클릭 가능한 `<div>` 대신 `<button>`을 쓰는가,
  `<label htmlFor>`와 `<input id>`가 짝이 맞는가, 아이콘만 있는 버튼에 `aria-label`이 있는가, 모달/
  드롭다운을 직접 구현했다면 포커스 이동(`ref.current.focus()`)과 `Esc` 닫기를 처리했는가.
  라우팅에 `react-router` 등을 쓴다면 페이지 전환 시 포커스가 본문 최상단으로 돌아가는지도 확인한다.
- **다크모드(판단 순서 6번)**: Tailwind면 `dark:` variant, CSS 변수 기반이면 `prefers-color-scheme`
  미디어쿼리나 테마 토글 상태를 확인한다 — 라이트 모드 스타일만 고치고 다크 모드 검증을 빠뜨리기 쉽다.
- **상태별 UI(흔한 실수의 "로딩/빈/에러 상태 누락")**: React라면 데이터 요청 하나당 최소
  로딩/에러/빈 배열 세 가지 분기가 JSX에 실제로 존재하는지 확인한다 — "성공 케이스"만 렌더링하는
  컴포넌트가 실사용에서 가장 먼저 무너진다.

## 흔한 실수 — 화면을 보기 전에 이 목록과 대조한다

- **레이아웃 없이 색상부터 바꿈** — 위 판단 순서를 어긴 전형적인 경우.
- **여백이 요소마다 다른 임의의 px 값** — spacing scale을 벗어난 값(예: `13px`, `22px`)이 보이면
  가장 가까운 scale 값으로 맞춘다.
- **버튼/카드 스타일이 화면마다 미묘하게 다름** — 같은 역할의 컴포넌트는 프로젝트 전체에서 하나의
  스타일만 갖는다.
- **정보 위계가 폰트 크기 하나로만 표현됨** — 굵기/색/여백을 함께 써서 위계를 중복 인코딩한다(색만
  믿지 않는 게 접근성 원칙과도 같은 이유).
- **좁은 화면에서 텍스트/버튼이 겹치거나 잘림** — 반응형을 클래스만 넣고 실제로 확인 안 했을 때
  생긴다.
- **포커스 상태(키보드 탐색 시 outline)가 지워져 있음** — `outline: none`만 걸고 대체 스타일을 안
  넣은 경우 흔하다.
- **로딩/빈 상태/에러 상태가 디자인에서 빠짐** — "정상 케이스"만 디자인하고 나머지 상태는 손대지
  않은 화면이 실사용에서 제일 먼저 무너진다.

## 이 스킬이 다루지 않는 것

- **문구/카피 작성**은 다루지 않는다 — 텍스트 내용이 아니라 그 텍스트가 화면에서 어떻게 배치·표현되는지만 다룬다.
- **화면과 무관한 백엔드 로직 변경**은 다루지 않는다.

# Mobile Developer — Expo/React Native 개발

모바일 앱 개발은 웹 개발보다 실패 지점이 많다 — JS 코드, 네이티브 빌드 설정, 시뮬레이터/에뮬레이터
환경, 모노레포의 패키지 매니저(특히 Bun/pnpm의 isolated linker)까지 여러 층이 얽혀서, 같은 증상(예:
"스타일이 안 먹는다")이 완전히 다른 층의 원인에서 나올 수 있다. 이 스킬은 그 층들을 순서대로
의심하는 절차와, 한 번 겪은 환경 문제를 프로젝트별로 기록해 다음에 반복하지 않게 하는 장치
(`mobile-guide.md`)를 제공한다.

## 작업 절차

1. **`mobile-guide.md`부터 찾는다 — 있으면 그게 최우선, 없으면 만든다.** 작업 중인 모바일 앱 프로젝트
   루트(`app.json`/`package.json`이 있는 위치, 모노레포면 해당 앱 폴더)에서 `mobile-guide.md`를 찾는다.
   - **있으면**: 이 스킬의 일반 원칙보다 그 파일 내용이 우선한다 — 이 프로젝트가 이미 실측으로 확인한
     사실(JDK 버전, 패키지 버전, 알려진 버그와 해결법)이기 때문이다. 특히 "알려진 환경 이슈" 절을
     먼저 훑어서, 지금 맞닥뜨린 증상이 이미 기록된 것인지 확인한다 — 있으면 그 해결법을 바로 적용하고
     처음부터 디버깅하지 않는다.
   - **없으면**: `references/mobile-guide-template.md` 구조로 새로 만든다. 이 시점에는 프로젝트 개요와
     로컬 실행 방법만 채울 수 있고, "알려진 환경 이슈" 절은 비워둔다 — 실제로 겪지 않은 문제를
     추측해서 채우지 않는다.
2. **새로운 환경 문제를 발견하고 해결하면, 그 자리에서 바로 `mobile-guide.md`에 기록한다.** 작업을 다
   끝낸 뒤 몰아서 기록하지 않는다 — 기록을 미루면 잊거나 생략하기 쉽다. 기록 형식: 증상 → 원인 → 해결
   → (선택) 왜 이 프로젝트에서만 발생했는지. "왜"가 있어야 다음에 비슷하지만 다른 증상을 만났을 때도
   같은 원인 계열인지 판단할 수 있다.
3. **아래 "흔한 실패 지점"을 원인 후보로 놓고, 증상에 맞는 층부터 의심한다.** 각 항목의 "왜"를 이해하면
   이 목록에 없는 새 증상도 같은 사고방식으로 좁혀나갈 수 있다.
4. 코드 작성 자체는 일반 개발 규율(단순성, 최소 변경 등)을 따른다 — 이 스킬과 함께 `developer` 스킬이
   활성화돼 있으면 그쪽 원칙을 그대로 따르고, 이 스킬은 모바일 특유의 지식만 보탠다.

## 흔한 실패 지점과 원인

### 1. "빌드는 성공했는데 데이터가 안 뜬다"

**원인 후보 1순위: 로컬 백엔드 API 서버가 안 떠 있다.** 모바일 앱은 웹과 달리 브라우저 devtools로
네트워크 탭을 바로 못 보니, 데이터 로딩 실패가 마치 앱 코드 버그처럼 보인다. 앱 코드를 의심하기 전에
API 서버 포트가 실제로 리스닝 중인지(`lsof -ti :<포트>`) 먼저 확인한다. iOS 시뮬레이터는 `localhost`가
macOS 호스트를 그대로 가리키지만, **Android 에뮬레이터는 `localhost`가 에뮬레이터 자신을 가리킨다** —
호스트 macOS에 접속하려면 `10.0.2.2`를 써야 한다. 이 차이를 놓치면 iOS에서는 되고 Android에서만
안 되는 증상으로 나타난다.

### 2. "스타일(className/style)이 컴파일은 되는데 화면에 전혀 반영 안 된다"

이건 원인 층이 특히 많아서, 증상만 보고 바로 코드를 고치려 하지 말고 **컴파일 파이프라인을 아래
순서로 하나씩 실측 확인**한다(중간 단계를 건너뛰고 추측하면 엉뚱한 곳을 계속 고치게 된다):
1. JSX 변환 자체가 되는가(babel 트랜스폼 적용 확인).
2. 스타일 컴파일 결과물(CSS→RN 변환 등)이 실제로 올바른 값을 담고 있는가.
3. 그 컴파일 결과가 런타임에 실제로 주입되는가.

**Bun/pnpm 같은 isolated linker를 쓰는 모노레포에서는, 1~3번이 전부 정상으로 보이는데도 최종 결과가
안 나오는 경우가 있다 — 이때는 "같은 패키지의 서로 다른 물리 사본"을 의심한다.** 원리: 스타일링
라이브러리(NativeWind 등)의 babel 플러그인이 JSX를 변환하며 `import ... from
"저-라이브러리/jsx-runtime"` 같은 **bare import를 새로 생성**하는 경우, 이 import는 "원래 작성한
소스 파일의 위치"를 기준으로 Metro가 다시 resolve한다. isolated linker는 **직접 선언되지 않은 전이
의존성**에는 앱 전용 `node_modules`에 심볼릭 링크를 만들지 않으므로, 이 bare import가 디렉터리 상위
탐색 끝에 (linker 도입 이전부터 남아있던, 또는 다른 워크스페이스가 설치한) **모노레포 루트의 잔재
사본**으로 잘못 resolve될 수 있다. 그러면 "컴파일 시점에 쓰는 사본"과 "런타임에 실제로 로드되는
사본"이 물리적으로 다른 파일이 되어, 컴파일 결과가 전혀 다른 곳에 쌓이고 화면은 계속 비어 보인다.

확인 방법:
```bash
# 패키지가 여러 해시로 중복 설치돼 있는지
find node_modules/.bun -maxdepth 1 -iname "<패키지명>@*"
# 루트 node_modules/<패키지명>이 심볼릭 링크가 아니라 진짜 디렉터리면 잔재 사본 의심
file node_modules/<패키지명>   # "directory"면 잔재, 심볼릭 링크면 정상
# 실제 앱 소스 위치에서 그 패키지가 어디로 resolve되는지 직접 확인
node -e "console.log(require.resolve('<패키지명>', {paths: ['<앱 src 경로>']}))"
```
해결: 그 패키지를 **앱의 `package.json`에 직접 의존성으로 추가**(스타일링 라이브러리가 실제로 쓰는
것과 같은 버전)하고 재설치 — isolated linker가 앱 전용 심볼릭 링크를 올바르게 만들어준다. 루트에
잔재 사본이 있었다면(`node_modules/` 자체는 git 추적 대상이 아니므로) 삭제해도 안전하다.
`metro.config.js`에 `resolver.unstable_enableSymlinks = true`를 켜두는 것도 심볼릭 링크를 realpath로
통일해 비슷한 클래스의 문제를 예방하는 데 도움이 된다.

**node_modules 안의 파일을 직접 열어 디버깅 코드를 심을 때는, Metro를 완전히 재시작(`--clear`)해야
반영된다** — 앱을 재연결하거나 Fast Refresh만 트리거하면 예전 번들을 계속 서빙해서 "고쳤는데도 안
바뀐다"는 잘못된 결론에 이르기 쉽다.

**이 층들을 다 확인했는데도 원인이 안 잡히면, 모노레포 밖에 완전히 새로운 최소 재현 프로젝트를
만든다**(같은 프레임워크 버전, 같은 설정으로 `bunx create-expo` 등). 거기서 재현되면 라이브러리/SDK
버전 자체의 버그(모노레포와 무관), 재현 안 되면 이 모노레포 특유의 설정(워크스페이스 심볼릭 링크,
Metro `watchFolders` 등) 문제로 범위가 좁혀진다.

### 3. "`app.json`을 고쳤는데 네이티브 동작이 그대로다" (예: 태블릿 지원, 아이콘, 권한)

Expo는 CNG(Continuous Native Generation) 방식이다 — `app.json`은 네이티브 프로젝트(`ios/`,
`android/`)를 생성하는 **설계도**일 뿐, 이미 생성된 네이티브 프로젝트에 자동으로 다시 반영되지
않는다. `app.json`만 고치고 기존 `ios/`/`android/` 폴더로 계속 빌드하면 변경이 반영 안 된 것처럼
보인다. 해결은 둘 중 하나:
- `npx expo prebuild --clean`으로 네이티브 프로젝트를 통째로 재생성한다(가장 확실하지만 느리고, 그
  폴더에 직접 해둔 다른 커스터마이징이 있으면 같이 날아간다).
- 해당 설정이 매핑되는 네이티브 파일을 직접 찾아 고친다(더 빠르고 최소 변경). 예: iOS의
  `supportsTablet`은 Xcode 프로젝트의 `TARGETED_DEVICE_FAMILY`(`1`=iPhone 전용, `"1,2"`=Universal)에
  대응한다. `ios/`, `android/` 폴더가 보통 `.gitignore` 대상이라(CNG 프로젝트의 정상 구성), 이렇게
  직접 고친 값은 다음에 그 폴더를 재생성하면 사라진다 — **그러니 `app.json` 쪽도 반드시 같이
  고쳐서** 다음 prebuild에도 유지되게 한다. `app.json`을 빠뜨리고 네이티브 파일만 고치면, 나중에
  누군가 `prebuild --clean`을 돌렸을 때 같은 버그가 조용히 재발한다.

### 4. Android 빌드가 CMake 단계에서 알 수 없는 이유로 실패한다

최신 JDK(21+)가 Android Gradle Plugin의 네이티브(CMake) 빌드 태스크와 호환되지 않아
`WARNING: A restricted method in java.lang.System has been called` 같은 메시지와 함께 실패하는
경우가 있다 — iOS 빌드는 JDK를 아예 안 써서 이 문제를 가린다. Android 빌드 명령에만 JDK 17을
지정한다(`JAVA_HOME=<jdk17 경로> npx expo run:android`). 머신의 다른 도구가 최신 JDK를 기대할 수
있으니 전역 `JAVA_HOME`/셸 프로필은 바꾸지 않는다.

### 5. Android 에뮬레이터에 앱 설치가 `INSTALL_FAILED_INSUFFICIENT_STORAGE`로 실패한다

`avdmanager`로 만든 기본 AVD는 데이터 파티션이 작아(예: 800M) 디버그 APK 설치에도 공간이 부족할 수
있다. `~/.android/avd/<AVD이름>.avd/config.ini`에서 `disk.dataPartition.size`를 늘린 뒤(예: 4096M)
`emulator -avd <AVD이름> -wipe-data`로 재부팅해야 반영된다(기존 데이터 파티션을 다시 만들어야 크기가
바뀐다 — 단순 재시작으로는 안 바뀐다).

### 6. 시뮬레이터/에뮬레이터를 조작(탭·입력)해서 확인해야 하는데 GUI 자동화 도구가 없다

Xcode.app(Simulator.app GUI 포함) 없이 CoreSimulator 런타임만 headless로 설치된 환경이거나, `idb`가
없으면 탭/스와이프/키보드 입력을 시뮬레이션할 방법이 없다(`xcrun simctl`은 부팅·스크린샷·앱 설치·
딥링크만 지원하고 터치 입력은 지원하지 않는다). 이럴 땐 각 화면으로 **직접 딥링크**해서 스크린샷으로
초기 렌더링을 확인하는 방식으로 대체한다:
```bash
xcrun simctl openurl <device> "<bundle-id>://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081%2F<경로>"
```
주의점:
- 이 방식은 iOS의 "앱에서 열겠습니까?" 확인 알럿을 매번 띄우는데, 탭으로 닫을 수 없다 — 알럿이 화면
  일부를 가려도 뒤에서는 정상적으로 네비게이션이 진행되므로 무시하고 스크린샷을 찍으면 된다. 단
  `justify-center` 등으로 화면 정중앙에 배치된 콘텐츠는 알럿과 정확히 겹쳐 안 보일 수 있다 — 이때는
  코드 리뷰(로직이 올바른지, 관련 로그에 에러가 없는지)로 보완한다.
- 세션이 필요한 화면(로그인 후 화면 등)에 세션 없이 딥링크하면 인증 리다이렉트가 정상 동작인지
  확인하는 용도로 쓸 수 있다 — 이것도 검증의 일부다.
- **이 방식은 "화면이 올바르게 렌더링되는가"만 확인하지, "폼에 값을 입력하고 제출하는 조작"까지는
  확인하지 못한다.** 그 한계를 사용자에게 명확히 알린다 — 실제 조작 테스트가 필요하면 GUI가 있는
  환경이나 실기기, 또는 `idb`를 설치한 환경에서 다시 확인해야 한다고 말한다.

### 7. 태블릿/큰 화면 레이아웃이 코드는 맞는데 실기기 폭 기준 분기가 항상 "좁은 화면"으로만 잡힌다

`useWindowDimensions()` 등으로 화면 폭을 재는 반응형 로직 자체는 맞는데, iPad 시뮬레이터에서 앱이
전체화면이 아니라 **iPhone 호환성 모드(좁은 창)**로 뜨고 있지 않은지 먼저 확인한다(2번 항목과 같은
"태블릿 미지원" 원인, `app.json`의 `supportsTablet` 누락). 반응형 분기 로직을 아무리 고쳐도, 애초에
좁은 창으로 렌더링되고 있으면 절대 "넓은 화면" 조건에 도달하지 못한다 — 레이아웃 코드보다 먼저
네이티브 설정을 확인한다.

## mobile-guide.md 작성/갱신

구조는 `references/mobile-guide-template.md` 참고. 핵심은:
- **실제로 겪고 해결한 것만 적는다** — 이상적으로 있을 법한 이슈를 미리 채우지 않는다.
- 각 항목은 증상(어떤 요청/작업에서 발생했는지) → 원인 → 해결(정확한 명령/설정값) → 왜 이 항목이
  필요한지를 담는다. "왜"가 없으면 나중에 "이 규칙이 지금도 유효한가"를 판단할 수 없다.
- 프로젝트의 버전(Expo SDK, RN, 패키지 매니저)이 바뀌면 옛 항목이 더 이상 안 맞을 수 있다 — 오래된

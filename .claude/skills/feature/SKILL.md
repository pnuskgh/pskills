# Feature Skill

`features/` 폴더는 기능(feature) 단위로 하위 폴더를 만들고, 그 안에 "이 문서가 어느 단계
산출물인가"를 이름으로 드러낸 `.md` 파일들을 모아 이 프로젝트의 작업 지시 이력을 남긴다.
`prompt` 스킬(`prompts/NNN_이름.md`, 임의의 순번)의 개선판이다 — 번호 대신 단계 이름을 쓰면
폴더만 봐도 그 기능이 어디까지 진행됐는지 알 수 있다.

## 폴더 구조

두 형태 중 하나를 쓴다.

```
features/{feature명}/{단계}.md
features/{app명}/{feature명}/{단계}.md
```

- `{feature명}`: 관련 문서를 그루핑하는 기능 이름(예: 사용자관리, 구조개선).
- `{app명}`: 여러 feature가 함께 속하는 애플리케이션 이름(예: crm) — 관련 feature가 하나의
  애플리케이션 아래 여럿 있을 때만 이 계층을 쓴다.
- 같은 프로젝트 안에서도 어떤 feature는 `features/` 바로 아래, 어떤 feature는
  `features/{app명}/` 아래 있을 수 있다. 새 feature 폴더를 만들 때: 이미 관련
  `features/{app명}/` 폴더가 있으면 그 아래에, 특정 애플리케이션에 종속되지 않으면
  `features/` 바로 아래에 만든다. 애매하면 추측하지 말고 사용자에게 물어본다.
- **`{feature명}`과 `{app명}`은 `features/` 바로 아래에서 같은 이름 공간을 공유한다** — 예를
  들어 `features/crm/`이 이미 "crm"이라는 단일 feature(그 아래 바로 `요구사항.md` 등이 있는
  폴더)로 쓰이고 있다면, 같은 이름으로 "crm"이라는 app을 새로 만들어 그 아래 여러 feature를
  묶으려 하면 한 폴더 안에 파일과 하위 feature 폴더가 섞여 헷갈린다. 새 폴더 이름이 기존
  feature명·app명과 겹치면 진행 전에 사용자에게 확인한다.
- `{feature명}`/references/ 폴더에는 해당 feature와 관련된 외부 자료나 참고 문서를 둔다. 예를 들어 요구사항 명세서, 디자인 가이드, 법령 문서 등을 저장할 수 있다.

## 파일 이름 순서

같은 feature 폴더 안 파일은 다음 순서를 따른다. 각 단계는 생략될 수 있다.

1. `요구사항.md`
2. `분석설계.md` (또는 `분석.md`와 `설계.md`로 분리)
3. `개발.md`, `디자인.md`, `SEO.md`, `법령준수.md`, `보안.md` — 이 다섯은 서로 순서가 없는
   병렬 산출물이다. 필요한 것만 만든다.
4. `배포.md`
5. `유지보수.md`

이 순서는 파일을 전부 만들라는 뜻이 아니라, 아래 처리 절차에서 "다음 파일"을 판단하는
기준이다.

### 업무 접두어 (`{업무}_{단계}.md`) — 선택

파일 이름은 접두어 없이(`요구사항.md`) 쓸 수도 있고, `{업무}_` 접두어를 붙여(`홈화면_요구사항.md`)
쓸 수도 있다 — **같은 feature 폴더 안에 두 형태가 섞여 있어도 된다.**

- **언제 쓰는가**: 하나의 feature 폴더 안에서 서로 독립적인 작업 갈래(업무) 여러 개가 각자
  요구사항→분석설계→...→유지보수 단계를 밟아야 할 때. 예를 들어 `features/디자인개선/` 폴더
  하나에 "홈화면"(`홈화면_요구사항.md`, `홈화면_분석설계.md`, ...)과 "로그인화면" 같은 별개
  업무가 나란히 진행될 수 있다 — 매번 새 feature 폴더를 만들지 않고 관련 있는 개선 작업들을
  한 폴더에 묶어 두면서도 각 업무의 진행 단계를 파일 이름만으로 구분할 수 있다.
- **`{업무}`란**: 그 feature 폴더 안에서 이 문서 묶음을 그루핑하는 짧은 이름(예: 홈화면). 위
  "폴더 구조"절의 `{feature명}`/`{app명}` 작명 기준과 같은 감각으로 정한다 — 폴더 이름을 새로
  또 만드는 대신, 폴더 안에서 한 단계 더 작은 묶음을 파일 이름으로 표현하는 것이다.
- **접두어 없는 파일**은 그 feature의 "기본" 갈래로 취급한다 — 업무가 하나뿐이면 접두어를 붙일
  필요가 없다(기존 관례 그대로 계속 쓸 수 있다).
- **구분자**: `{업무}`와 `{단계}` 사이는 언더스코어(`_`) 하나. 단계 이름(`요구사항`, `분석설계`
  등)은 고정 어휘라, 파일 이름 끝이 그중 하나와 정확히 일치하는지로 접두어 유무를 판별한다
  (`SEO.md`처럼 원래 대문자 약어인 단계 이름도 그대로 유지).
- **처리 절차(아래)에서 "가장 최근 파일"을 찾을 때는 같은 업무 접두어(또는 둘 다 접두어 없음)를
  가진 파일끼리만 비교한다** — 서로 다른 업무의 파일 순서를 섞지 않는다. 자세한 판단 기준은
  처리 절차 2번 참고.

## 프런트매터

`prompt` 스킬과 형식이 같다. 각 파일 맨 위에 다음을 둔다.

```yaml
---
prompt-before: |
  (이 파일을 만들기 위해 사용자가 실제로 입력한 프롬프트 원문)
prompt:
  - |
    (이 파일이 만들어진 뒤, 이 파일과 관련해 처리한 프롬프트 원문 1)
  - |
    (프롬프트 원문 2 ...)
prompt-after: |
  (다음 파일을 만들기 위해 사용자가 실제로 입력한 프롬프트 원문)
---
```

## 트리거

**이 프로젝트가 `features/` 폴더 관례를 쓸 때만** 적용된다(그 아래가 `features/{feature명}/`
평면 구조든 `features/{app명}/{feature명}/` 중첩 구조든 상관없다) — 대상 프로젝트에
`prompts/NNN_이름.md`(번호 붙은 파일) 관례가 있다면 그건 `prompt` 스킬의 영역이니 이 스킬을
쓰지 않는다. 아래 두 가지 트리거가 있다.

### 1. "처리해" — 배치 반영

사용자가 **"feature 파일을 처리해"** 또는 **"\*.md 파일을 처리해"**(예: "사용자관리/개발.md
파일을 처리해", 또는 그냥 "이 md 파일을 처리해")처럼 요청하면 적용한다. 그동안 쌓인, 아직
프런트매터에 반영 못 한 프롬프트들을 한 번에 몰아서 기록하는 배치 작업이다 — 대화 이력을
거슬러 올라가 채운다(아래 "처리 절차" 참고).

### 2. 파일 기반 작업 지시 — 즉시 반영

**"처리해"라는 말이 없어도**, 사용자가 features/ 아래 특정 파일을 근거로 삼아 작업을 지시하면
그 자리에서 즉시 이 스킬을 적용한다. 예: "features/사용자관리/요구사항.md
보고 로그인 기능 구현해줘", "개발.md의 3단계부터 이어서 작업해", "이 분석설계.md 문서 기준으로
다음 단계 진행해", "홈화면_분석설계.md 파일을 작성해"(업무 접두어가 붙은 파일도 동일하게 적용).
**왜 필요한가**: 이런 요청도 그 파일의 실제 작업 이력의 일부인데, 매번 "처리해"를
별도로 요청해야만 기록된다면 사용자가 잊기 쉽고 기록이 실제 작업보다 뒤처진다 — 작업이 일어나는
바로 그 순간에 같이 기록해야 이력이 항상 최신 상태로 유지된다.

- 지목된 파일이 이미 프런트매터를 갖고 있으면(과거에 만들어진 파일) 이 요청 원문을 그 파일의
  `prompt` 배열 끝에 추가한다.
- 지목된 파일이 이번에 처음 만들어지는 것이면(요청 자체가 새 파일을 전제로 함) `prompt-before`에
  이 요청 원문을 넣고, 그 직전에 만들어진 파일이 있으면 그 파일의 `prompt-after`를 같은 원문으로
  채운다.
- 프런트매터를 기록한 뒤에는 반드시 **실제 요청된 작업(코드 구현, 설계 등)을 그대로 수행한다** —
  이 스킬은 기록만 하고 끝나지 않는다. "처리해"(배치 반영)와 달리 이 트리거는 처음부터 "지금
  이 작업을 하라"는 요청이므로, 작업 자체가 이 스킬 실행의 본체다.
- 새 파일 자체를 "작성해"달라는 요청("사용자관리/개발.md 파일을 작성해")은 이 트리거가 아니라
  일반적인 파일 생성 작업이다 — 다만 그 요청이 다른 기존 파일(예: 요구사항.md)을 근거로 삼는다면,
  그 근거 파일 쪽에는 여전히 위 규칙대로 기록한다.

## 처리 절차

"처리해"라는 요청은 두 가지를 함께 할 수 있다: **(A) 프런트매터 갱신**(항상 수행)과
**(B) 파일 본문 수정**(요청 내용에 본문을 바꿔야 할 지시가 섞여 있을 때만 수행).

1. **대화 이력에서 실제 프롬프트 원문을 확인한다.** 요약이 아니라 사용자가 입력한 문장을 그대로
   옮긴다. 압축(compaction)으로 원문을 더 이상 확인할 수 없는 구간이 있으면 채우지 말고 어디까지
   반영했는지 알린다.
2. **대상 feature 폴더를 정한다**(사용자가 지목했거나, 최근 작업 중이던 폴더). 그 폴더 안에서
   **가장 최근에 만들어진 파일**(마지막으로 채워진 `prompt` 항목이 있거나 `prompt-after`가
   비어 있는 파일)을 찾는다 — `prompt` 스킬의 "번호가 가장 큰 파일" 자리를 대신한다. 파일 이름
   순서(위 표)가 아니라 **실제 생성 순서**를 따른다 — 3단계(개발/디자인/SEO 등)처럼 병렬
   파일이 여럿이어도, 그중 어느 게 먼저 만들어졌는지가 기준이다.
   - **업무 접두어가 섞여 있으면 같은 업무끼리만 비교한다**(위 "업무 접두어" 절). 어느 업무를
     기준으로 찾을지는: (a) 사용자가 이번 요청에서 특정 파일을 지목했으면 그 파일의 접두어를
     그대로 쓴다, (b) 지목이 없으면 바로 직전까지 이어오던 대화가 다루던 업무를 쓴다, (c) 그마저
     불분명하면 폴더 전체(접두어 무관)에서 가장 최근 파일을 기준으로 삼되, 여러 업무의 파일이
     최근에 섞여 있어 애매하면 추측하지 말고 어느 업무를 말하는지 사용자에게 묻는다.
3. 이번 "처리해" 이전의 사용자 프롬프트를 순서대로 훑으며 하나씩 분류한다.
   - **새 `features/.../*.md`(또는 `features/{app명}/.../*.md`) 파일을 만들라는 요청**이면: 그 요청
     원문을 새 파일의 `prompt-before`로 채운다(`prompt`는 빈 배열, `prompt-after`는 비워 둔다).
     2번에서 찾은 "바로 직전 파일"이 있으면 그 파일의 `prompt-after`를 **같은** 원문으로 채운다.
   - **가장 최근 파일과 관련된 후속 요청**(그 파일 내용을 수정/확인/질문/구현)이면: 그 파일의
     `prompt` 배열 끝에 요청 원문을 새 항목으로 추가한다(기존 항목은 지우지 않는다). 본문을
     바꿔야 하는 지시라면(위 (B)) 프런트매터만 채우지 말고 **실제로 본문도 그 지시대로
     수정**한다 — 지시 내용과 본문이 어긋나지 않게 만든다.
   - 어느 feature 폴더인지, `features/` 바로 아래인지 `features/{app명}/` 아래인지, 또는
     새 파일과 기존 파일의 연관성이 애매하면 추측해서 채우지 말고 사용자에게 물어본다.
4. 프런트매터 값에는 콜론(`:`), 따옴표, 코드 블록 등 YAML을 깨뜨릴 수 있는 문자가 섞이기 쉬우므로
   항상 리터럴 블록 스칼라(`|`)로 적는다.
5. 다 채운 뒤에는 어떤 파일의 프런트매터를 바꿨는지, 본문도 수정했다면 무엇을 바꿨는지 간단히
   요약해서 보고한다.

## 처음 실행할 때 (과거분 소급)

기존 파일에 아직 이 프런트매터가 전혀 없으면, 별도로 "지금까지 것도 다 채워줘" 같은 소급
요청이 없는 한 **처음 "처리해"를 요청받은 시점 이후의 프롬프트만** 새로 반영한다 — 과거
파일들의 프런트매터를 압축 이전 기록까지 뒤져 억지로 복원하지 않는다.

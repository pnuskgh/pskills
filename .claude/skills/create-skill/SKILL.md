# Create Skill — 스킬 작성기

스킬 1개를 처음부터 끝까지(요구사항 파악 → 위치 결정 → 중복 검토 → 작성 → 검증) 만드는 스킬. 에이전트 팀·오케스트레이터가 필요한 대규모 하네스 구축 요청이면 `harness` 스킬로 넘긴다.

## 워크플로우

### 1. 요구사항 파악

다음이 불명확하면 사용자에게 먼저 묻는다 — 추측해서 채우지 않는다.
- **목적**: 이 스킬이 정확히 어떤 작업을 자동화/가이드하는가?
- **트리거 상황**: 사용자가 실제로 어떤 문장으로 이 작업을 요청할 것 같은가? (2~3개 예시 문장)
- **산출물**: 파일 생성인가, 코드 수정인가, 분석/보고인가?

### 2. 위치 결정

| 위치 | 적합한 경우 |
|------|-----------|
| `~/.claude/skills/{name}/`(전역) | 여러 프로젝트에서 재사용할 개인 작업 습관/규율 (예: developer, prompt) |
| `프로젝트/.claude/skills/{name}/`(프로젝트 로컬) | 이 저장소의 파일 구조·컨벤션에 종속된 작업 (예: 이 저장소의 `apps/*_web` 스캐폴딩) |

애매하면 사용자에게 묻는다. 기본 추정: 특정 프로젝트의 파일 경로/컨벤션을 전제로 하면 프로젝트 로컬, 범용 작업 규율이면 전역.

### 3. 중복 검토

신규 생성 전, 아래 두 위치를 모두 훑어 이름/역할이 겹치는 스킬이 있는지 확인한다.
- `~/.claude/skills/*/SKILL.md`
- `프로젝트/.claude/skills/*/SKILL.md`

| 상황 | 조치 |
|------|------|
| 기존 스킬이 신규 기능을 완전히 포함 | 신규 생성 금지 — 기존 스킬 확장을 제안 |
| 기존 스킬이 부분 포함, 일반화 가능 | 기존 스킬을 일반화하여 확장 |
| 기능 범위가 다름 또는 의도된 특화 | 신규 생성 진행 |

### 4. Description 작성 — 적극적 트리거 유도

Description은 스킬의 유일한 트리거 메커니즘이다 — Claude는 `available_skills` 목록에서 name + description만 보고 스킬 사용 여부를 결정하며, 트리거를 보수적으로 판단하는 경향이 있다. 그래서 description은 약간 "pushy"하게 쓴다: **스킬이 하는 일** + **구체적 트리거 문구/상황** + **유사하지만 트리거하면 안 되는 경계**를 모두 담는다.

**나쁜 예:** `"PDF 문서를 처리하는 스킬"` — 모호하고 트리거 상황이 없다.
**좋은 예:** `"PDF 파일 읽기, 텍스트/테이블 추출, 병합, 분할, 회전, 워터마크, 암호화 등 모든 PDF 작업을 수행. .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것."`

### 5. 본문 작성 원칙

| 원칙 | 설명 |
|------|------|
| **Why를 설명하라** | "ALWAYS/NEVER" 대신 이유를 전달한다 — LLM은 이유를 이해하면 엣지 케이스에서도 올바르게 판단한다. |
| **명령형으로 작성** | "~한다", "~하라" 형태. 스킬은 지시서이지 설명서가 아니다. |
| **일반화하라** | 특정 예시에만 맞는 좁은 규칙 대신 원리를 설명한다. |
| **Lean하게 유지** | SKILL.md 본문은 500줄 이내 목표. 컨텍스트 윈도우는 공공재 — 모든 문장이 "이게 없으면 실수하는가?"를 통과해야 한다. |
| **반복 코드는 번들링** | 매번 동일하게 작성하는 헬퍼가 있으면 `scripts/`에 미리 넣는다. |

**Progressive Disclosure**: SKILL.md는 항상 로드되므로 개요·워크플로우만 담고, 도메인별 세부사항이나 긴 참고자료는 `references/`로 분리해 필요할 때만 로드되게 한다.

```
skill-name/
├── SKILL.md (필수 — YAML frontmatter + 워크플로우)
├── scripts/    (선택 — 반복/결정적 작업용 실행 코드)
├── references/ (선택 — 조건부 로딩하는 참고 문서, 300줄 이상이면 목차 포함)
└── assets/     (선택 — 출력에 쓰이는 템플릿/이미지)
```

**부가 문서를 만들지 않는다**: README.md, CHANGELOG.md, INSTALLATION_GUIDE.md 같은 문서는 스킬에 넣지 않는다 — 스킬은 SKILL.md 하나(+ 필요 시 scripts/references/assets)로 자기 완결적이어야 하며, 그런 부가 문서는 에이전트가 아니라 사람을 위한 것이라 트리거 시 로드되어도 쓸모가 없다.

더 깊은 작성 패턴(출력 형식 정의, 예시 작성, 스크립트 번들링 판단 기준, 데이터 스키마 표준, 스킬 재사용 설계 등)이 필요하면 `references/skill-writing-guide.md`를 읽는다.

### 6. 작성 및 검증

1. `{위치}/.claude/skills/{name}/SKILL.md`를 frontmatter(`name`, `description` 필수) + 본문으로 작성한다.
2. **트리거 검증**: should-trigger 문장 2~3개(다양한 표현), should-NOT-trigger 문장 1~2개(비슷하지만 다른 스킬이 맞는 경계 사례)를 만들어 description이 이를 구분할 수 있는지 검토한다.
3. 사용자에게 생성된 파일 경로와 description을 요약 보고한다. 실제 실행 테스트는 별도 요청 시에만 수행한다(과도한 자동 검증 금지).

실행 테스트(with-skill vs baseline 비교, assertion 채점, 반복 개선 루프)나 20개 규모의 트리거 eval처럼 본격적인 검증이 필요하면 `references/skill-testing-guide.md`를 읽는다.

## 산출물 체크리스트

- [ ] 위치 결정(전역/프로젝트 로컬)을 사용자와 확인함
- [ ] 기존 스킬과 중복 검토 완료
- [ ] `description`이 적극적으로 작성됨 (하는 일 + 트리거 상황 + 경계)
- [ ] 본문이 명령형·Why-first로 작성되고 500줄 이내
- [ ] 불필요한 README/CHANGELOG 등 부가 문서를 만들지 않음

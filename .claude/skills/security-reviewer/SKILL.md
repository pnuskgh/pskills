# Security Reviewer — 보안 점검 (보안 컨설턴트)

보안 컨설턴트의 코드 보안 점검은 자동 스캔만으로도, 수동 검토만으로도 완결되지 않는다 — 자동 스캔은
알려진 패턴만 잡고, 수동 검토는 범위를 넓게 훑지 못한다. OWASP Secure Code Review 방법론은 범위
설정 → 위협 모델링 → 자동 스캔 → 수동 검토 → 리스크 등급화 → 보고/보완 계획 순서를 권장한다 — 아래
단계는 이를 따른다. 위협 모델을 먼저 세우지 않고 바로 스캔부터 하면, 스캐너가 놓치는 "이 서비스만의"
로직 결함(권한 우회, 인증 흐름 오류 등)을 놓치기 쉽다.

**전제**: 사용자가 소유했거나 점검 권한이 명확한 코드/시스템에만 적용한다. 실제 공격 실행이 필요한
침투 테스트(모의해킹)는 별도의 승인된 계약 범위에서만 하고, 이 스킬에서는 다루지 않는다.

## 1. 범위 설정 (Scoping)

- 점검 대상: 어떤 코드베이스/서비스/API인가? 신규 개발 코드인지, 기존 운영 코드인지.
- 데이터 민감도: 개인정보, 인증정보, 결제정보 등 민감 데이터를 다루는가 — 다룬다면 우선순위가
  올라간다.
- 규제 요건이 있으면(개인정보보호법, PCI-DSS 등) 표시만 하고 상세 준수 여부 판단은
  `regulatory-compliance-review`가 있으면 그쪽에 맡긴다.

불명확하면 추측해서 전체 저장소를 훑지 말고, 범위를 먼저 확인한다.

## 2. 위협 모델링 (Threat Modeling)

- 진입점(entry point)을 나열한다: 외부에서 들어오는 입력(API, 폼, 파일 업로드, 3rd-party webhook 등).
- 신뢰 경계(trust boundary)를 그린다: 어디서부터 "신뢰할 수 없는 입력"으로 취급해야 하는가.
- **STRIDE**로 위협을 분류한다: Spoofing(신원 위장) / Tampering(변조) / Repudiation(부인) /
  Information Disclosure(정보 노출) / Denial of Service(서비스 거부) / Elevation of Privilege
  (권한 상승).
- 이 단계의 산출물은 "무엇을 중점적으로 봐야 하는가"의 우선순위 목록이다 — 3~4단계에서 이 목록을
  기준으로 검토한다.

## 3. 자동 스캔 (Automated Scanning)

가능하면 아래 세 종류를 구분해서 실행/확인한다. 프로젝트에 이미 CI에 붙어 있는 도구가 있으면 그
결과를 재사용하고 중복 실행하지 않는다.

| 종류 | 목적 | 예시 도구 |
| :--- | :--- | :--- |
| SAST(정적 분석) | 소스 코드 자체의 취약 패턴(인젝션, 안전하지 않은 함수 등) | Semgrep, CodeQL, 언어별 린터의 보안 룰셋 |
| SCA(구성요소 분석) | 의존성(3rd-party 라이브러리)의 알려진 취약점(CVE) | `npm audit`, `pip-audit`, Dependabot, OSV-Scanner |
| Secret Scanning | 코드/커밋 이력에 하드코딩된 키·토큰·비밀번호 | gitleaks, trufflehog |

자동 스캔 결과는 노이즈(오탐)가 섞이므로 그대로 보고하지 않는다 — 4단계에서 실제 악용 가능성을
검토해 걸러낸다. **모노레포/워크스페이스 환경에서는 특히 주의한다**: SCA 도구가 취약 패키지를
워크스페이스 이름으로만 묶어 보여주면, 그 워크스페이스가 실제로 물고 있는 게 취약 버전인지 잠금
파일(`bun.lock`/`package-lock.json` 등)에서 **직접 해석된 버전**을 확인하기 전에는 보고하지 않는다
— 같은 이름의 패키지가 워크스페이스마다 다른 버전으로 호이스팅/중첩될 수 있어, 점검 대상 서비스는
이미 패치된 버전을 쓰는데 무관한 다른 워크스페이스(예: 전혀 다른 도구 체인)의 취약 버전 때문에
전체가 취약하다고 오탐하기 쉽다.

## 4. 수동 코드 검토 (Manual Review)

자동 스캔이 못 잡는 "이 서비스만의" 로직 결함을 찾는다. **OWASP Top 10:2025** 카테고리를 체크리스트로
쓴다.

| 코드 | 카테고리 | 확인 포인트 |
| :--- | :--- | :--- |
| A01 | Broken Access Control (SSRF 포함) | 권한 검증 누락, 다른 사용자 리소스 접근 가능 여부, 서버가 사용자 입력 URL로 요청을 보내는 지점 |
| A02 | Security Misconfiguration | 기본 계정/설정 방치, 불필요한 기능 노출, 에러 메시지에 내부 정보 노출 |
| A03 | Software Supply Chain Failures | 검증 안 된 의존성/빌드 파이프라인, 서명 검증 없는 아티팩트 |
| A04 | Cryptographic Failures | 평문 저장/전송, 취약한 알고리즘, 하드코딩된 키 |
| A05 | Injection | SQL/명령어/템플릿 인젝션 — 입력값을 직접 조합해 쿼리/명령을 만드는 지점 |
| A06 | Insecure Design | 설계 단계부터 보안 통제가 빠진 흐름(예: 비밀번호 재설정 로직에 인증 단계 누락) |
| A07 | Authentication Failures | 세션 관리, 비밀번호 정책, 다단계 인증 우회 가능성 |
| A08 | Software and Data Integrity Failures | 검증 없는 역직렬화, 무결성 검사 없는 업데이트/CI 파이프라인 |
| A09 | Security Logging and Alerting Failures | 보안 이벤트 로그 부재, 탐지·알림 체계 없음 |
| A10 | Mishandling of Exceptional Conditions | 예외/에러 처리 미흡으로 인한 fail-open, 논리 오류 |

체크리스트를 기계적으로 다 채우려 하지 말고, 2단계 위협 모델에서 우선순위가 높다고 표시한 부분부터
본다.

## 5. 리스크 등급 산정 (Risk Rating)

- 발견 항목마다 **영향도(Impact) × 발생 가능성(Likelihood)**로 등급을 매긴다 — 심각/높음/중간/낮음.
- 민감 데이터(2단계에서 표시한)에 닿는 결함은 등급을 낮추지 않는다.
- 재현 방법(reproduction steps)을 남긴다 — 등급만 매기고 재현 근거가 없으면 나중에 담당자가 검증할
  수 없다.

## 6. 보고 및 보완 계획 (Reporting & Remediation Plan)

- 발견 항목을 등급 순으로 정렬해 보고한다.
- 항목마다 보완 방법을 구체적으로 제시한다 — "안전하게 처리하세요" 같은 추상적 조언이 아니라 실제
  코드 수준의 수정 방향을 제시한다.
- 심각/높음 등급은 즉시 조치, 중간/낮음은 다음 스프린트로 나눠 **우선순위가 있는 로드맵**으로
  정리한다 — 전부 "지금 당장"으로 뭉뚱그리지 않는다.
- **로드맵 각 행에 고유 번호를 매긴다**(우선순위 단계와는 별개 컬럼) — 같은 단계 안에 항목이
  여러 개면 사용자가 "1번 처리해"처럼 번호로 하나씩 지목해 나중에 순차 처리를 요청할 수 있어야
  한다. 우선순위 라벨(즉시/다음 스프린트 등)만으로는 같은 라벨을 공유하는 행이 여러 개일 때
  구분할 방법이 없다.
- 수정이 끝났다고 끝난 게 아니다 — 수정 후 같은 항목을 재검증(해당 취약점이 실제로 막혔는지 확인)하는
  단계를 계획에 포함한다. 외부 API 호출처럼 새 의존성이 추가되는 보완책은 그 의존성이 실패했을 때
  (타임아웃 등) 원래 기능 자체가 막히는 fail-closed가 되지 않는지도 재검증 항목에 넣는다.

## 7. 상시 보안 가이드 (Security Guide) — 보고서와는 별개 산출물

**보고서(6단계 산출물)와 "앞으로 지켜야 할 규칙"은 성격이 다른 문서다** — 보고서는 이번 점검
시점의 발견·이력이라 날짜가 붙고 갱신될수록 길어지지만, 개발자·디자이너가 매일 참고할 문서로는
무겁다. 대상 프로젝트에 이미 `design-guide.md`류(디자인/코드 스타일처럼 "작업 중 상시 참고하는
규칙 문서")가 있거나, 점검이 일회성이 아니라 계속 개발되는 서비스라면 **점검 결과에서 재발
가능성이 있는 교훈만 뽑아 별도의 상시 가이드 문서**(예: `security-guide.md`)로 만든다:

- 보고서의 "발견 항목"·"보완 로드맵"이 아니라, 그 발견이 남긴 **일반화된 규칙**만 옮긴다(예:
  "세션 쿠키의 httpOnly/secure/sameSite를 끄지 않는다", "관리자 라우트는 그룹 단위로 미들웨어를
  건다") — 특정 파일·특정 사고의 조사 과정은 보고서 쪽에 남기고, 가이드에는 결론만 간결하게 둔다.
- 개발자용 규칙과 디자이너/UX용 규칙을 구분한다 — 보안 문제의 상당수는 코드가 아니라 화면 설계
  (에러 메시지가 계정 존재 여부를 흘리는지, 파괴적 관리자 동작에 확인 단계가 있는지, 시크릿을
  화면에 평문 노출하는지)에서 나온다.
- 프로젝트의 기존 가이드 문서(`design-guide.md` 등)가 있으면 같은 위치·같은 형식(코드 레퍼런스
  포함, "이 문서를 갱신하는 기준" 절 등)을 따라 만들어 자연스럽게 나란히 참조되게 한다. 프로젝트의
  진입 문서(`CLAUDE.md`/`AGENTS.md`)에도 그 가이드로 가는 참조를 추가해 실제로 발견되게 한다 —
  링크만 있고 아무도 안 보는 문서는 만든 의미가 없다.
- 가이드가 아직 없어도 되는 경우(일회성 스크립트 점검, 팀 없이 혼자 유지보수하는 프로젝트 등)까지
  기계적으로 만들지 않는다 — 상시 참고할 사람이 있는 프로젝트에서만 값어치가 있다.

## 출력 형식

```markdown
# {대상} 보안 점검 보고서

## 0. 범위
- 점검 대상:
- 데이터 민감도:
- 규제 요건:

## 1. 위협 모델 요약
- 진입점:
- 신뢰 경계:
- STRIDE 기준 우선순위:

## 2. 발견 항목
| 등급 | OWASP 분류 | 위치(파일/함수) | 내용 | 재현 방법 | 보완 방법 |
| :--- | :--- | :--- | :--- | :--- | :--- |

## 3. 보완 로드맵
| 번호 | 우선순위 | 항목 | 담당(제안) | 목표 시점 | 재검증 방법 |
| :--- | :--- | :--- | :--- | :--- | :--- |
```

보고서와 별개로, 7단계 기준에 해당하면 `{project}/security-guide.md`(또는 그 프로젝트의 기존
가이드 문서 명명 관례를 따른 이름)를 같이 만들거나 갱신하고, 진입 문서에서 그 파일로 가는 참조를
추가한다.

## 제약

- 이 스킬은 코드/설계 차원의 취약점 발견과 보완 계획까지다 — 실제 공격을 실행하는 침투 테스트,
  라이브 서비스에 대한 부하/DoS 테스트는 하지 않는다.
- 운영 중 이미 발생한 침해 사고 대응은 `incident-response`의 몫이다 — 이 스킬은 사고 전 예방적
  점검에 집중한다.
- 법적 규제 준수 여부(개인정보보호법 등)의 최종 판단은 `regulatory-compliance-review`가 있으면
  그쪽에 맡기고, 여기서는 "확인 필요" 리스크로만 표시한다.
- 근거 없이 취약점을 지어내지 않는다 — 자동 스캔 결과든 수동 검토든, 실제 코드 위치와 재현 근거를
  남길 수 없는 항목은 "의심"으로만 표시하고 확정 취약점으로 보고하지 않는다.

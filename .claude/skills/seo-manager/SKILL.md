# SEO Manager — 검색엔진 최적화 및 사이트 등록

SEO는 "검색엔진이 사이트를 크롤링·색인할 수 있는가"(기술 SEO)가 먼저고, 그다음이 "등록해서 색인
속도를 높이는가"(사이트 등록)다. 순서를 바꿔 기술 SEO가 안 된 사이트를 먼저 등록하면 각 콘솔이
"크롤링 오류"만 계속 보고한다 — 그래서 아래 단계를 순서대로 밟는다.

## 1. 범위 확정

- **`seo-guide.md`부터 찾는다.** 작업 중인 프로젝트 루트(`design-guide.md`/`security-guide.md`가
  있다면 그것과 같은 위치)에 이 파일이 있으면 먼저 읽는다 — 이미 등록 완료한 검색엔진, 소유확인
  방식, sitemap.xml/robots.txt를 만드는 코드 위치, 과거에 내린 canonical 정책 같은 결정을 다시
  조사하는 건 낭비다. 없으면 5절 기준에 따라 이번 작업 결과로 새로 만든다.
- **대상 사이트**: 등록/최적화할 도메인(또는 서브도메인)을 확인한다.
- **대상 검색엔진**: Google/Naver/Daum(카카오)/Bing 중 전부인지 일부인지 확인한다 — 사용자가 이미
  지정했으면 추측하지 않고 그대로 따른다.
- **유료광고와 구분한다**: "광고를 위한 SEO"라는 표현이 나오면 자연검색 노출 개선을 뜻하는 것인지,
  실제 유료 검색광고(SEM) 세팅을 원하는 것인지 확인한다 — 후자면 이 스킬의 범위 밖이라고 알린다.

## 2. 기술 SEO 사전 점검 (등록보다 먼저)

각 콘솔에 등록해도 아래가 안 되어 있으면 색인이 안 되거나 순위에 불리하다. 등록 전에 먼저 확인하고
빠진 것은 만든다.

| 항목 | 확인/조치 | 안 되어 있으면 생기는 문제 |
| :--- | :--- | :--- |
| HTTPS | 인증서 적용 여부 | 신뢰도 하락, 일부 브라우저 경고 |
| `robots.txt` | 루트에 존재, 중요 페이지를 실수로 차단하지 않았는지 | 크롤러가 아예 사이트를 못 읽음 |
| `sitemap.xml` | 정규(canonical) URL만 포함, 5만 개/50MB 이하 | 새 페이지 색인이 느려짐 |
| `<title>`/`<meta name="description">` | 페이지마다 고유하게 작성 | 검색 결과 스니펫 품질 저하 |
| canonical 태그 | 중복 URL(파라미터, `www` 유무 등)에 정규 URL 지정 | 중복 콘텐츠로 순위 분산 |
| 구조화된 데이터(JSON-LD) | 상품/게시글/FAQ 등에 schema.org 마크업 | 리치 리절트(별점, FAQ 등) 노출 기회 상실 |
| Core Web Vitals (LCP/INP/CLS) | PageSpeed Insights로 상위 트래픽 페이지부터 확인 | 구글 랭킹 시그널에 불리 |
| 모바일 대응 | 반응형 여부 | 모바일 검색 노출 불리 |

`robots.txt`/`sitemap.xml`/메타태그/JSON-LD를 직접 코드에 반영하는 작업은 이 스킬이 수행한다. 사이트
구조 자체를 바꿔야 하는 문제(느린 페이지 등)는 원인만 짚고 실제 수정은 해당 코드 작업(`developer`
등)으로 넘긴다.

## 3. 검색엔진별 사이트 등록

4개 콘솔은 소유확인 방식과 등록 절차가 서로 다르다. 상세 절차(소유확인 방법별 장단점, 사이트맵 제출
경로, 색인 소요 기간)는 `references/search-engine-registration.md`에 있다 — 등록을 실제로 진행할
때 그 문서를 읽는다.

핵심 원칙만 요약하면:

- **소유확인 토큰을 코드에 심는 건 이 스킬이 한다**(HTML 메타태그 삽입, 인증 파일 업로드). 각 콘솔
  웹 UI에 로그인해서 토큰을 발급받는 것 자체는 사용자 계정으로만 가능하므로 사용자에게 요청한다 —
  계정 자격증명을 대신 입력하려 하지 않는다.
- **Google에 먼저 등록하고 Bing은 거기서 가져온다.** Bing 웹마스터 도구는 Google 서치콘솔에서 바로
  Import할 수 있어 별도 소유확인이 필요 없다 — 순서를 바꿔 Bing을 먼저 하면 이중 작업이 된다.
- **네이버는 소유확인 → RSS 제출 → 사이트맵 제출 순서를 지킨다.** 순서를 건너뛰면 등록은 되어도
  색인이 느려진다.
- **Daum(카카오)은 별도 웹마스터 도구가 아니라 심사 기반 등록 폼이다.** 즉시 반영되는 게 아니라 심사를
  거치므로, 정보 불일치로 반려될 수 있는 항목(사이트명, 카테고리, 대표 URL)을 미리 사용자와 확인한다.
- 등록 URL은 각 서비스가 개편을 자주 하므로, 진행 시점에 검색으로 현재 URL을 다시 확인한다 — 오래된
  URL을 그대로 안내하지 않는다.

## 4. 등록 후 확인

- 색인 소요 기간은 엔진마다 다르다(구글 수 시간~수 일, 네이버 1~4주, 다음 최대 5영업일 심사). 등록
  직후 "왜 아직 검색에 안 나오냐"는 질문에는 이 기준으로 정상 범위인지 먼저 판단한다.
- 각 콘솔의 "크롤링 오류"/"색인 생성 안 됨" 리포트는 정기적으로 확인해야 하는 항목이라고 안내한다 —
  1회 등록으로 끝나는 작업이 아니다.
- 사이트 구조가 크게 바뀔 때(URL 체계 변경, 신규 섹션 추가)는 sitemap.xml을 갱신하고 재제출해야
  한다는 점을 함께 안내한다.

## 5. 상시 SEO 가이드 (`seo-guide.md`) — 이번 작업 요약과는 별개 산출물

이번에 무엇을 확인·등록했는지 사용자에게 보고하는 것과, "다음에 이 프로젝트에서 SEO를 다시 만질
때 참고할 상시 문서"는 성격이 다르다 — 전자는 대화로 충분하지만, 후자를 안 남기면 다음 세션이
등록 현황·기술 SEO 설정을 처음부터 다시 조사하게 된다(어느 검색엔진에 이미 등록했는지, 소유확인
토큰을 어디에 심어 뒀는지는 코드만 봐서는 알 수 없는 경우가 많다).

- **기록 대상**: 재조사 비용이 있는 사실과 결정만 남긴다 — 등록 완료된 검색엔진과 각각의 소유확인
  방식(메타태그/파일 업로드 등, 실제 토큰 값은 비밀값이면 제외), `sitemap.xml`/`robots.txt`를
  만드는 코드 위치(정적 파일인지 라우트가 동적으로 생성하는지), canonical 정책(예: "정규 호스트는
  항상 `www.` 고정"), 이 프로젝트 구조상 SEO에 영향을 주는 특이사항(예: SPA라 초기 HTML에 메타
  태그가 비어 있고 클라이언트에서 채움). 이번에 발견했지만 다음에 참고할 필요가 없는 세부 조사
  과정은 넣지 않는다 — 그건 사용자에게 보고한 대화 내용으로 충분하다.
- **갱신 시점**: 검색엔진 등록을 새로 완료했거나, 기술 SEO 설정(사이트맵 생성 방식, canonical 처리
  등)을 코드로 바꿨을 때. 메타 설명 문구 하나 고치는 것처럼 재발 가능성이 없는 일회성 수정까지
  기계적으로 갱신하지 않는다.
- **위치·형식**: 프로젝트에 `design-guide.md` 같은 기존 가이드 문서 관례가 있으면 같은 위치·형식
  (코드 레퍼런스 포함)을 따라 나란히 두고, 없으면 프로젝트 루트에 새로 만든다. 진입 문서
  (`CLAUDE.md`/`AGENTS.md`)에 이 파일로 가는 참조가 없다면 추가한다 — 그래야 다음 세션이 실제로
  찾아 읽는다.
- 아직 만들 필요 없는 경우: 이번이 처음이자 유일한 SEO 작업이라 "다음"이 없을 것으로 보이는
  프로젝트, 또는 메타 설명 한 줄 수정처럼 정말 사소한 일회성 요청. 이런 경우까지 강제로 만들지
  않는다.

## 제약

- 유료 검색광고(SEM/PPC) 캠페인 설계·집행은 다루지 않는다 — 순수 오가닉 SEO만 다룬다.
- 계정 로그인, 결제 정보 입력, 소유권 확인 버튼 클릭처럼 사용자 계정으로만 할 수 있는 조작은 대신
  수행하지 않는다 — 코드/파일 준비까지가 이 스킬의 범위고, 콘솔 조작은 사용자가 한다.
- 콘텐츠 자체의 주제 선정·발행 일정은 `content-calendar`의 몫이다.
- 순위 상승을 보장하는 표현을 쓰지 않는다 — SEO는 노출 가능성을 높이는 작업이지 순위를 확정하는
  작업이 아니다.

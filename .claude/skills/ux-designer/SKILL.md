# UX Designer — 사용자 경험 설계

UI(`designer` 스킬의 영역)는 "보기 좋은가"를 묻고, UX는 "쓰기 쉬운가"를 묻는다. 둘은 다른 질문이라
순서도 다르다 — **동선과 정보구조가 틀리면 아무리 예쁘게 칠해도 사용자는 헤맨다.** 그래서 이 스킬은
항상 "사용자가 지금 뭘 하려고 여기 왔는가"에서 시작해서, 그 목표까지 가는 경로를 설계한 뒤에야 화면
구현(`designer`)으로 넘긴다.

## `designer` 스킬과의 역할 분담

같은 "화면 작업" 요청이라도 질문의 층위가 다르면 다른 스킬이 맡는다.

| 질문 | 담당 |
| :--- | :--- |
| 사용자가 이 화면에 왜 왔고, 다음에 뭘 해야 하는가? 단계가 너무 많지 않은가? | **ux-designer**(이 스킬) |
| 메뉴 구조·네이밍이 사용자의 멘탈모델과 맞는가? | **ux-designer** |
| 에러가 났을 때 사용자가 복구할 방법이 있는가? | **ux-designer** |
| 레이아웃·여백·색상·타이포그래피가 이 프로젝트 관례를 따르는가? | `designer` |
| 반응형·다크모드·대비(contrast)가 맞는가? | `designer` |

**순서**: UX 결정(이 스킬)이 먼저고, 그 결정을 화면으로 굳히는 건 `designer`의 "구조(Structure)"
단계와 맞닿는다 — 완전히 새 화면/플로우를 만드는 요청이면 이 스킬로 동선·정보구조를 먼저 정하고,
그 다음 `designer`를 불러 레이아웃·비주얼을 입힌다. 이미 있는 화면의 "느낌"만 요청받았으면(색 바꿔줘,
여백 넓혀줘) 이 스킬을 거치지 않고 바로 `designer`로 간다 — 모든 화면 요청이 UX 분석을 거칠 필요는
없다.

## 작업 절차

### 1. `ux-design-guide.md`부터 찾는다 — 있으면 그게 기준, 없으면 만든다

작업 중인 프론트엔드 프로젝트 루트(`design-guide.md`/`security-guide.md`가 있다면 그것과 같은
위치)에서 `ux-design-guide.md`를 찾는다.

- **있으면**: 이 프로젝트가 이미 내린 UX 결정(타깃 사용자, 핵심 태스크, 자주 쓰는 플로우 패턴,
  과거에 겪은 사용성 문제와 그 해결책)이 이 스킬의 일반 원칙보다 우선한다. 매번 처음부터 사용자
  조사를 재구성하지 않는다.
- **없으면**: 이번 작업에서 파악한 내용(타깃 사용자가 누구인지, 핵심 태스크가 무엇인지, 아래 2~4절
  적용 결과)을 바탕으로 `ux-design-guide.md`를 새로 만든다 — 구조는 `references/ux-design-guide-template.md`
  참고.

### 2. 사용자의 목표와 멘탈모델부터 확정한다

화면/컴포넌트를 보기 전에 먼저 답한다 — 답이 불명확하면 사용자에게 묻는다, 추측해서 설계하지 않는다.

- 이 화면/플로우에 들어온 사용자는 **지금 무엇을 끝내려 하는가**? (가입 완료, 결제 완료, 정보 확인 등)
- 그 목표를 이미 이 서비스/유사 서비스에서 어떤 식으로 경험해봤을 가능성이 높은가? (예: "장바구니"는
  이커머스 어디서나 비슷하게 동작할 거라고 기대한다 — 그 기대를 깨면 학습 비용이 생긴다)
- 이 작업이 **일회성**(가입)인지 **반복 작업**(매일 쓰는 대시보드)인지 — 반복 작업일수록 클릭 수·
  단계 수를 줄이는 효율성이, 일회성일수록 친절한 설명(온보딩)이 더 중요해진다.

### 3. 사용성 휴리스틱을 순서대로 대조한다

Nielsen의 10가지 사용성 휴리스틱을 이 프로젝트 맥락으로 재구성한 체크리스트다. 전부 한 번에
적용하려 하지 말고, 지금 보는 화면/플로우에 실제로 해당하는 항목만 짚는다.

1. **시스템 상태의 가시성** — 지금 로딩 중인지, 저장됐는지, 실패했는지 사용자가 항상 알 수 있는가?
   (버튼을 눌렀는데 아무 반응이 없으면 사용자는 다시 누른다 — 중복 제출 버그의 UX적 원인이 여기
   있는 경우가 많다.)
2. **현실 세계와의 일치** — 사용자의 용어/개념 순서를 쓰는가, 서비스 내부 구현 용어("ACTION 타입"
   같은)를 그대로 노출하지 않는가?
3. **사용자 제어와 자유** — 실수로 들어온 플로우를 되돌리거나 빠져나갈 방법(취소/뒤로가기/닫기)이
   항상 있는가? 삭제처럼 되돌릴 수 없는 작업은 확인 단계가 있는가?
4. **일관성과 표준** — 이 프로젝트 안에서, 그리고 플랫폼 관례(웹이면 일반적인 웹 패턴, 모바일이면
   iOS Human Interface Guidelines/Material Design 같은 플랫폼 관용구)에서 같은 동작이 같은 방식으로
   표현되는가? 플랫폼 관례를 벗어나면 그 자체가 학습 비용이다 — 특별한 이유 없이 플랫폼 기본값과
   다르게 만들지 않는다.
5. **오류 예방** — 에러 메시지로 안내하기보다, 애초에 틀린 입력을 못 하게(또는 하기 전에 경고하게)
   막을 수 있는가? (예: 비활성화된 제출 버튼보다 "왜 아직 제출할 수 없는지"를 보여주는 쪽이 낫지만,
   아예 실수할 수 없는 입력 형태(날짜 피커 등)가 자유 텍스트보다 먼저 검토할 선택지다.)
6. **기억보다 인식** — 이전 화면에서 본 정보를 사용자가 기억해서 다음 화면에 다시 입력하게 만들지
   않는가? 선택지는 가능하면 입력보다 노출(드롭다운, 자동완성)로 제공하는가?
7. **유연성과 효율성** — 초보자용 안내(긴 폼, 단계별 마법사)와 숙련자용 지름길(단축키, 한 번에
   처리)이 공존할 수 있는가? 반복 작업일수록 이 항목 비중이 커진다(2절 참고).
8. **심미적이고 미니멀한 디자인** — 이 화면에 지금 목표와 무관한 정보/선택지가 섞여 있어 주의를
   분산시키지 않는가? (시각적 아름다움 자체는 `designer`의 몫이지만, "이 요소가 여기 있어야
   하는가"라는 **포함 여부 판단**은 UX의 몫이다.)
9. **오류 인식·진단·복구** — 에러 메시지가 "무엇이 왜 틀렸고 어떻게 고치면 되는지"까지 말해주는가,
   아니면 "오류가 발생했습니다"처럼 원인 불명인가?
10. **도움말과 문서** — 꼭 필요한 경우가 아니면 도움말 없이도 이해되는 게 최선이지만(과도한 설명은
    오히려 인지 부하), 복잡한 작업(최초 설정, 규제 관련 동의 등)은 그 자리에서 바로 참고할 수 있는
    짧은 설명이 있는가?

### 4. 태스크 플로우의 단계 수를 센다

2절에서 정한 목표에 도달하기까지 **실제로 몇 번의 상호작용(클릭/탭/입력)이 필요한지** 세어 본다.
단계를 줄일 수 있는지 먼저 검토하고(불필요한 확인 화면, 중복 입력, 필수가 아닌데 필수처럼 보이는
필드), 줄일 수 없는 단계라면 진행 상황(몇 단계 중 몇 번째)을 보여줘 사용자가 "얼마나 남았는지"
알게 한다. **단계를 줄이는 것과 단계를 숨기는 것은 다르다** — 뒤로 미룬 복잡도가 더 늦은 시점에
한꺼번에 터지면(예: 마지막 단계에서야 결제 실패 사유를 알림) 그게 더 나쁜 경험이다.

### 5. 필요하면 WebSearch로 현재 업계 관례를 확인한다

이 스킬의 체크리스트(3절)는 시간이 지나도 변하지 않는 일반 원칙(Nielsen 휴리스틱)이지만, **구체적인
상호작용 관례는 플랫폼/시대에 따라 바뀐다** — 알고 있다고 가정하지 말고 아래 경우엔 검색으로
확인한다.

- 플랫폼 공식 가이드라인(iOS Human Interface Guidelines, Material Design, 웹 접근성 최신 권고 등)이
  이 상황에 대해 뭐라고 하는지 — 버전이 올라가며 관례가 바뀌는 경우가 흔하다(예: 제스처 관례, 바텀시트
  사용 기준).
- 이 도메인(결제, 가입, 구독 취소, 금융/의료처럼 규제가 있는 분야 등)에 특화된 널리 알려진 UX
  패턴·이탈 원인 조사 결과가 있는지 — 일반론만으로 설계하면 그 도메인 특유의 함정(예: 구독 취소
  플로우에서 의도적으로 단계를 늘리는 "다크 패턴"과, 그게 왜 장기적으로 신뢰를 깎는지)을 놓칠 수
  있다.
- 특정 UI 패턴(무한 스크롤 vs 페이지네이션, 모달 vs 전체화면 등)의 장단점에 대한 최신 합의가
  궁금할 때 — 이 스킬 안에 모든 패턴의 트레이드오프를 미리 다 적어둘 수 없으므로, 그때그때 확인한다.
- **검색하지 않아도 되는 경우**: 이미 `ux-design-guide.md`에 이 프로젝트의 결정으로 적혀 있는 사항,
  또는 Nielsen 10휴리스틱처럼 안정적인 일반 원칙으로 충분히 판단되는 사항 — 모든 질문을 검색으로
  해결하려 하지 않는다.

### 6. 결정한 내용을 `designer`로 넘기거나 직접 구현한다

- 완전히 새 화면/플로우를 만드는 작업이면, 1~5절에서 정한 동선·정보구조·단계 구성을 가지고
  `designer` 스킬을 호출해 레이아웃·비주얼을 입힌다(이 스킬이 "무엇을, 어떤 순서로"를 정하면
  `designer`가 "어떻게 보일지"를 정한다).
- 기존 화면의 UX만 고치는 작업(단계 순서 변경, 에러 메시지 문구 추가, 빈 상태 안내 추가, 확인 단계
  삽입 등)이면 직접 코드를 수정한다 — 비주얼 스타일은 기존 화면의 기존 컴포넌트/클래스를 그대로
  재사용하고 새로 디자인하지 않는다(새 비주얼이 필요해지면 그때 `designer`를 부른다).
- **실제로 플로우를 끝까지 밟아본다.** 코드만 고치고 끝내지 않는다 — dev 서버를 띄워 처음부터
  끝까지(에러 케이스 포함) 실제로 조작해보고, 그래도 안 밟아볼 사정이 있으면(수동 QA가 어려운
  환경 등) 그 사실을 숨기지 말고 명시한다.

### 7. `ux-design-guide.md`를 최신 상태로 유지한다

이번 작업에서 앞으로도 참고될 결정(타깃 사용자 정의, 핵심 태스크 목록, 이 프로젝트가 택한 플로우
패턴, 과거에 겪은 구체적인 사용성 문제와 그 해결 — 예: "사용자가 N단계에서 반복 이탈해 M으로
줄임")을 내렸다면 파일에 반영한다. 이번 화면 하나에만 해당하는 지엽적 결정은 적지 않는다.

## 흔한 실수 — 설계를 보기 전에 이 목록과 대조한다

- **목표를 안 묻고 바로 화면부터 그림** — 2절을 건너뛴 전형적인 경우. "예쁜데 왜 안 쓰이는지"
  모르는 화면이 대개 이렇게 나온다.
- **단계 수는 안 줄이고 로딩 스피너만 추가** — 4절의 "줄이기"와 "숨기기"를 혼동한 경우.
- **에러 메시지가 "오류가 발생했습니다"로 끝남** — 9번 휴리스틱 위반. 원인과 다음 행동을 반드시
  같이 말한다.
- **플랫폼 관례를 이유 없이 거스름** — 4번 휴리스틱 위반. 독창성이 목적이 아닌 한 플랫폼 기본값을
  따른다.
- **되돌릴 수 없는 작업(삭제, 결제, 탈퇴)에 확인 단계가 없음** — 3번 휴리스틱 위반.
- **UX 결정과 비주얼 폴리싱을 동시에 하려다 둘 다 어중간해짐** — 역할 분담 표를 참고해 순서를
  지킨다.

## 이 스킬이 다루지 않는 것

- **시각적 폴리싱**(색상·여백·타이포그래피·반응형·다크모드)은 다루지 않는다 — `designer`로 넘긴다.
- **문구의 어휘 선택 자체(톤앤매너, 브랜드 보이스)**는 다루지 않는다 — 이 스킬은 "이 시점에 안내가
  필요한가/어떤 정보가 포함돼야 하는가"까지만 다루고, 정확한 단어 선택은 카피라이팅의 몫이다.
- **사용자 리서치 실행**(인터뷰 진행, 설문 설계·발송) 자체는 다루지 않는다 — 이미 존재하는 리서치
  결과나 데이터(이탈률, 고객 문의 등)를 해석해 설계에 반영하는 것까지가 범위다.
